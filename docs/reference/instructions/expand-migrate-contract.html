What each stage means, per kind of change

Concrete per migration kind — grounded in DarkBadge's job_type_taxonomy_v2 and activity_link_attempts cases.
Kind Expand Migrate Contract Purge
Schema / data Add the new column or table; dual-write on every write path; old column stays authoritative. Flip a flag so reads move to the new column; old column keeps being written as the safety net. Remove the toggle and dual-write code — old column stops being written, but stays in place, dormant. Once the pre-migration data has been ported to the new column, or it's archived/snapshotted or past its retention window — drop the old column. Its own, later release.
Message / API shape Add the new SQS field or shape; producers emit old and new together. Flag decides which shape is authoritative for new messages; consumers keep accepting both. Remove the old shape from producers and consumers. N/A — nothing physical to retire once Contract lands.
Feature / code path New path built dark behind a Release toggle; old path stays live. Toggle enabled for rollout; both paths still deployed. Codify Phase — delete the dark branch and the toggle. (Already documented.) N/A — Contract already removed everything.
Infra / site upgrade Stand up the new service or host alongside the old; traffic still 100% old. Router shifts traffic to the new host; old host stays warm for instant rollback. Stop routing to the old host entirely; power it off, cold — not yet destroyed. Once its data/config is confirmed backed up, or past retention — decommission and wipe the old host or volume.

The Feature / code path row is core/progressive_delivery.md's existing Toggle Types + Codify Phase doctrine — this ladder is that same shape, generalized to schema, message, and infrastructure changes, where the Migrate-stage reversibility guarantee has to be stronger: both representations must stay correct for the entire stage, not just "absent means dark."

Purge is a distinct release from Contract on purpose: Contract removes code risk (dual-write, the flag, the old read path); Purge removes data risk (the last copy). Either condition alone is enough to gate it — the data is confirmed ported to the new structure, or the old copy is safely elsewhere (a snapshot, a backup, past its retention window) — so a slow or partial backfill doesn't have to block Purge as long as the old data is recoverable some other way, and vice versa.
