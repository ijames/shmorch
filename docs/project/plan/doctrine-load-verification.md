**Doctrine load verification (proposal, not scoped)** — `core/` files carry prose `loads_when:` triggers, so whether a session actually loaded the doctrine that applied at the moment it applied is unobservable. A rule that exists in `core/` but never loads is indistinguishable from a rule that doesn't exist. Proposal to evaluate: stop asking the model to attest and observe instead — reads are tool calls, so a `PostToolUse` hook can append every `$SHMORCH_HOME/core/*.md` read to `timelog.md`, turning the question into a grep. Verification is then `observed ∩ expected`, and the expected half is the unsolved part: `loads_when` prose ("any code change") is a judgment, not a predicate. Cheapest approximation floated was a small trigger table keyed on observable events (edited a `test_*` file → `tdd.md` must appear in the read log), checked at wrap. Same log would also catch the inverse failure for free — core files loaded that didn't apply, i.e. context budget spent on nothing.

  - **Recursion caveat — the reason this can't be fixed with another doctrine file.** Three levels, each terminating only by leaving the layer: (1) a verifier written as doctrine is itself lazily loaded and has the exact failure mode it checks → must be a hook or script, not prose; (2) deciding whether a prose trigger fired is another model call → triggers must be observable events, not prose conditions; (3) model-graded evals are a model checking a model → assertions must be mechanical (file exists, test commit precedes code commit, grep hits). General rule: the checker must be a different kind of thing than the thing checked.
  - **Evaluate before building:** is the failure real? No evidence yet that lazy loading misses in practice — the observation is that nothing *would tell us* if it did. The read-log hook alone (level 1, no trigger table) is cheap and would answer that question with data before any enforcement is designed. Consider that a prerequisite spike.
  - **Open questions:** hooks are Claude Code-specific, which conflicts with `core/portability.md` — what does this degrade to on CLIs without hooks? Does the trigger table become another unpoliced list that drifts from `core/`? Does this belong to the eval-suite item instead, since evals verify behavior directly and make loading moot when they pass?
