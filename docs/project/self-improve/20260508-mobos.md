### Self-Improve Proposals — 2026-05-08

#### Proposal 1: Enforce Intent → Gherkin RED → PHPUnit RED → Code sequence

**Pattern:** The PUT replace quantity bug was fixed directly (code change first), then a
Behat scenario was written after the fact to verify. The correct sequence is:
Intent → write failing Gherkin (RED) → write failing unit tests (RED) → code → GREEN.
Writing tests after the fix means the tests never witnessed the bug; they were written to
pass a solution, not to catch a regression.

**Frequency:** This session (put-replace-fix). Likely recurring for any bug fix that has
observable loop-lifecycle behavior.

**File:** `~/.claude/skills/shmorch/workflows/build.md` — Step 2b or a new "Bug Fix" variant
of the build workflow.

**Change:** Add an explicit sequencing rule under "Before Starting Any Implementation":

> For bug fixes with observable lifecycle behavior (order loop, API interactions,
> user-facing outcomes):
> 1. Write the Gherkin scenario first. It must fail (RED) against the unfixed code.
> 2. If internal logic is also affected, write the PHPUnit test next. It must also fail.
> 3. Only then fix the code. Both tests must turn GREEN.
> 4. Commit code + tests together — never tests without code or code without tests.

**Improvement:** Ensures tests actually prove the bug existed, not just that the fix is
self-consistent. A test written after the fix can be trivially wrong and still pass.
