#### Proposal 1: Close track status in the same session the PR merges, not "next session"
**Pattern:** A track's build merges (PR merged, tests green) but its `index.md` `Status:` frontmatter is left `Open`, with an explicit note to close it "next session" — then the close-out doesn't happen until prompted again later.
**Frequency:** 2 occurrences —
- 2026-07-18 (`docs/project/session.md`): "New Home Page track's core build is merged (PR #105) and versioned (PR #106) — track itself still technically 'Open' pending the deferred close-out... Close out the New Home Page track properly — update its `index.md` status now that tests + browser verification are done."
- 2026-08-04 (`docs/project/session.md`, latest entry): "`docs/project/tracks/20260803-usability-philosophy-page` — Shipped, PR merged. Track can be closed/graduated next session."
**File:** `.shmorch/workflows/wrap.md` Step 6 (currently: "Check if any track statuses changed. If so, update `status:` frontmatter..."), possibly also `build.md`'s post-PR step (self-improve 2026-07-18 already added "pre-PR track-status sync" via skill PR #58 — that covers pre-PR, not post-merge close-out, which is why the pattern recurred after that fix).
**Change:** Add an explicit sub-step to wrap.md Step 6: "If the active track's PR merged this session and no blocking follow-up work remains on it, set `Status: Closed`/`Shipped` in its `index.md` now — do not defer to 'next session' unless there is a named, undone task blocking closure (state the task)." This turns "can be closed next session" into either "closed now" or a documented reason it can't be.
**Improvement:** Removes a recurring one-session lag where shipped tracks sit mislabeled as Open, which is exactly the kind of staleness Step 6.5 ("Graduate closed tracks") depends on to trigger — a track stuck on Open never reaches the graduation scan.
