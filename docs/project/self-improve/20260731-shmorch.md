#### Proposal 1: Deterministic VERSION conflict resolution during batch merges
**Pattern:** Every self-improve PR independently bumps `VERSION` to `YYYYMMDD.NN` off whatever `main` looked like when its branch was cut. When several branches are merged in sequence, every single merge step hits a `VERSION` conflict, because each branch's bump is stale the moment an earlier sibling merges.
**Frequency:** Anticipated in the 2026-07-30 session note ("every PR bumped VERSION to 20260730.02 independently off unmerged main... will conflict pairwise on merge") and then confirmed in the 2026-07-31 session note ("Resolved a VERSION collision at every single merge step") — 11 merges, 11 collisions. Two sessions, evidence in both `docs/project/session.md` entries.
**File:** `core/git-discipline.md`, "### After any PR merge" section (currently just says pull + rebase remaining branches, with no VERSION-specific guidance); cross-reference from `core/operations.md`'s "VERSION bump rule" (~line 58-63).
**Change:** Add a short subsection under "After any PR merge":
```
**VERSION conflicts are expected, not exceptional, during a merge sequence.** Every open
branch bumped VERSION off a now-stale main. When rebasing branch N onto a freshly-merged
main: always resolve the VERSION conflict by taking main's current value and incrementing
`.NN` by 1 — never keep the branch's own pre-rebase bump. Do this as part of the mandatory
post-merge rebase, not as an ad hoc fix at each conflict.
```
**Improvement:** Turns 11 improvised conflict resolutions into one documented, repeatable rule — removes the judgment call ("which VERSION value wins?") from every merge step in a batch sequence.

#### Proposal 2: self-improve.md doesn't enforce the existing branch-cap doctrine
**Pattern:** `core/git-discipline.md` already states: "Shmorch should not allow more than 2–3 branches open simultaneously on the skill repo... If you find yourself with 4+ open PRs, merge or close them before opening new work." `workflows/self-improve.md` Step 6 loops through proposals one at a time, branching + PR'ing each (`git checkout -b` → push → `gh pr create` → `git checkout main`, repeat) with no check against this cap and no reference to `git-discipline.md` at all.
**Frequency:** Directly caused the 2026-07-30 session to open 9 PRs (#75-#84) in one sitting, 3-4x over the documented cap — confirmed by the 2026-07-31 session needing a whole extra session just to merge the backlog. This is the same root event the existing plan item `docs/project/plan/watch-self-improve-and-backfill-execution.md` tracks from the *monitoring* angle ("don't let PRs stack up," "verify backfills reach consumers") — this proposal is the complementary *mechanical gate* that would have prevented the stack-up in the first place, so it is not a duplicate.
**File:** `workflows/self-improve.md`, Step 6 ("Skill-level changes" loop, currently steps 1-8 ending in `git checkout main` — return to main, do NOT merge).
**Change:** Before step 1 of the per-proposal branch loop, add a gate:
```
**Before branching for this proposal:** check open PR count against the branch cap in
`core/git-discipline.md` (`gh pr list --state open | wc -l`). If already at 2-3+ open
PRs, stop the proposal loop here — surface to the developer: "N proposals reviewed, M PRs
open (at/above cap). Merge or close existing PRs before continuing, or batch the
remaining proposals onto a single branch instead of one-per-PR."
```
**Improvement:** Makes self-improve respect a rule shmorch already wrote for itself, instead of silently violating it every time a proposal batch is larger than ~3 items.

#### Proposal 3: Inbox cleanup (Step 7) runs before the fix it's checking for has merged
**Pattern:** `workflows/self-improve.md` Step 7 classifies each `docs/inbox/*.md` item as ADDRESSED/PARTIAL/UNADDRESSED by grepping current skill files — but this runs during the same session that opens the PRs (Step 6), before any of them merge. So an item correctly classified UNADDRESSED at draft time never gets re-checked once its PR lands, and the inbox accumulates permanently-stale entries.
**Frequency:** Confirmed on 3 separate inbox files, all fully resolved by PRs merged 2026-07-31 but still present in `docs/inbox/` today:
  - `docs/inbox/pnpm-precedent-js-tooling.md` — content now lives verbatim in `core/js_tooling.md` (landed via PR #79).
  - `docs/inbox/settings-json-explanation.md` — `workflows/init.md:232` now explains `.claude/settings.json` (landed via PR #80).
  - `docs/inbox/session-recaps-files-touched.md` — `workflows/wrap.md:76` now has a "Files touched:" section (landed via PR #77).
**File:** `workflows/self-improve.md`, Step 7 ("Clear addressed inbox items and stamp").
**Change:** Add a line at the top of Step 7:
```
Before scanning for *new* classifications, first re-sweep any inbox item left PARTIAL or
UNADDRESSED by a prior self-improve run whose PRs have since merged (check
`docs/project/session.md` for "PR/commit status" lines listing merges since that item's
last-touched date) — re-classify against current (post-merge) skill files before adding
new findings.
```
**Improvement:** Prevents resolved proposals from sitting in the inbox indefinitely just because the merge happened in a later session than the one that drafted the fix — closes the gap between "proposal implemented" and "proposal removed from inbox."
