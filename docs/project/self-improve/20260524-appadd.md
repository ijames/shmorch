#### Proposal 1: NOTES.md addressed-item cleanup not firing reliably

**Pattern:** Items from April 2026 remain in `.shmorch/NOTES.md` (the project-local copy doesn't exist, but the skill's `NOTES.md` has items dated 2026-04-01 through 2026-05-07) despite those concerns being addressed in `shmorch-core.md`. The 2026-05-19 run produced 0 proposals — which is suspicious given 6+ items in NOTES.md — suggesting the step was skipped or treated as "nothing to do" rather than running the cleanup.

**Frequency:** 3 self-improve runs without cleanup; items at least 7 weeks stale.

**File:** `~/.claude/skills/shmorch/workflows/self-improve.md` — Step 7

**Change:** Rewrite Step 7 to make the cleanup mandatory and mechanical rather than inferential. Current wording says "check whether it has been fully addressed" — too vague. Replace with:

```markdown
## Step 7 — Clear addressed NOTES items and stamp

For each item in `.shmorch/NOTES.md` (or `~/.claude/skills/shmorch/NOTES.md` if no project override), determine its status by checking whether the concern appears in the current skill files:

```bash
# Check if concern appears addressed in skill
grep -r "<keyword from NOTES item>" ~/.claude/skills/shmorch/shmorch-core.md \
  ~/.claude/skills/shmorch/workflows/*.md 2>/dev/null | head -3
```

Status classification:
- **ADDRESSED** — the concern is reflected verbatim or substantively in a skill file. Remove the item now.
- **PARTIAL** — the concept exists but the specific proposal isn't implemented. Add `_(partial — <what's missing>)_` to the item and keep it.
- **UNADDRESSED** — not in any skill file. Keep as-is and include as a no-action observation in the proposals output.

If removing items: rewrite NOTES.md with only the surviving items. Do not leave addressed items "for the record" — that's what git history is for.

After cleanup, add one line to the proposals file:
```
### NOTES.md cleanup — <date>
Removed: <N items> (addressed). Kept: <M items> (unaddressed/partial).
```
```

**Improvement:** Self-improve produces accurate state instead of stale accumulation. The explicit grep check makes "addressed" a verifiable binary rather than a memory question.

#### Proposal 4: Transport/streaming constraints not in design workflow checklist

**Pattern:** SSE + Lambda buffering was discovered at build time — API Gateway buffers SSE responses, requiring Lambda Function URL instead. This constraint is a known AWS limitation that should surface at design time when Lambda appears in the architecture. The design workflow (`design.md`) has an architect role that reads `stack.md` and `docs/architecture/` but has no checklist for transport-layer constraints specific to the hosting platform.

**Frequency:** 1 direct occurrence (SSE/Lambda), but the pattern is general: any streaming, webhook, or long-polling requirement combined with a serverless/CDN/proxy layer can produce this class of failure. External API feasibility (Step 0.5 in `build.md`) catches API accessibility but not transport-layer constraints.

**File:** `~/.claude/skills/shmorch/workflows/design.md` — Step 2 (architect Task prompt, under Constraints section)

**Change:** Add an explicit transport constraints checklist to the architect's task prompt. In the "The design must cover" section, expand the "What must NOT change" bullet:

```markdown
- **Transport and runtime constraints:** If the feature involves any of the following, verify platform compatibility before recommending an approach:
  - Streaming responses (SSE, chunked transfer, WebSocket) → check whether the hosting platform or API gateway buffers responses (e.g. AWS API Gateway buffers SSE; Lambda Function URLs do not)
  - Webhooks or long-polling → check timeout limits on the host (Lambda: 15 min max; API Gateway: 29 sec)
  - File uploads or binary payloads → check payload size limits (API Gateway: 10 MB; Lambda direct: 6 MB sync / 256 KB async)
  - Background jobs → check cold-start and concurrency limits
  
  For each that applies: state the constraint explicitly in the Constraints section of the design doc and confirm the chosen approach works within it. Do not defer to build time.
```

**Improvement:** Catches platform-specific transport constraints at design time (minutes to catch) rather than build time (hours to discover and fix). The SSE/Lambda failure cost at minimum one session's worth of debugging and a refactor from API Gateway to Lambda Function URL.
