#### Proposal 1: Fix `go.md` CW-8's dead escalation check (wrong string + stale path)
**Pattern:** `workflows/go.md`'s "CW-8 — Escalate if this is recurring" step (added in PR #58, commit `cc2997a`, 2026-07-18) runs `grep -c "auto-wrapped on reentry" docs/state/timelog.md` to detect 3+ sessions in a row ending without a real wrap. Both parts of this check are wrong: (1) the string `"auto-wrapped on reentry"` originates from an older, superseded mechanism (`ad809e9`) — the actual auto-close markers in use today are `"auto-closed by stop hook — <branch> @ <last-commit>"` (`tools/stop.sh`) and `"auto-wrapped (guard: consecutive SESSION_START)"` (`tools/timelog.sh`'s self-healing guard); (2) the path is still the pre-migration `docs/state/timelog.md`, which no longer exists on any project using the current taxonomy (`docs/project/timelog.md`).
**Frequency:** Confirmed via direct evidence, not inference — `grep -c "auto-wrapped on reentry" docs/project/timelog.md` returns 0 matches against shmorch's own timelog; `grep -c "auto-closed by stop hook"` returns 4. The underlying friction pattern the check was meant to catch (sessions auto-closing without a real wrap) has recurred at least 4 times since PR #58 landed (2026-06-17, 2026-07-08→07-14, 2026-07-17, 2026-07-21 in shmorch's own `docs/project/timelog.md`), completely undetected because the check has been dead code since the day it was added.
**File:** `workflows/go.md` (CW-8 section)
**Change:** Replace the grep with the correct path and both real markers:
```bash
grep -cE "auto-closed by stop hook|auto-wrapped \(guard: consecutive SESSION_START\)" docs/project/timelog.md 2>/dev/null || echo 0
```
**Improvement:** The escalation nudge actually fires when it's supposed to, surfacing a real, recurring friction pattern (unwrapped sessions) that's currently invisible.

#### Proposal 6: New core doctrine — pnpm precedent for JS/TS projects
**Pattern:** `git worktree`-based parallel builds (used for multi-agent track work) don't share `node_modules` under plain npm — every new worktree needs a full fresh install before typechecking resolves correctly, and skipping it silently leaves type-checking broken (this happened on treeclusion: a worktree's `tsc` ran against the wrong/empty `node_modules` and missed a real error). Switching to pnpm (content-addressed store, hardlinked into each worktree) fixed it — installs went from "sometimes-skipped slow step" to ~1s regardless of worktree count. Developer confirmed this should be standing precedent, not a one-off fix.
**Frequency:** One occurrence, but the causal mechanism (worktrees + npm) applies to every JS/TS project using shmorch's parallel-build pattern — same class of gap as the pnpm/uv analogy suggests for Python.
**File:** New file `core/js_tooling.md`; add a row to `core/index.md`'s table
**Change:** Content already drafted (was written and validated on treeclusion, then backed out of a direct branch/PR per developer instruction to route through NOTES.md/self-improve instead): pnpm as default for new JS/TS projects and existing projects with no committed lockfile (adoption, not forced migration off an established npm/yarn project); rationale as above; a note that `uv` is the Python analogue deserving the same "prefer for new projects" precedent.
**Improvement:** Prevents a specific, already-observed class of silent build/typecheck breakage in multi-worktree JS/TS projects.
